# 多机器人运维平台架构思路

本文档用于讨论当前 G1 运维工具后续扩展到多机器人、多型号机器人时的产品形态和技术架构。当前软件运行稳定，后续演进建议以“不破坏现有能力、逐步抽象、先解决扩展瓶颈”为原则。

## 1. 背景

当前工具主要面向 Unitree G1 机器人，能力包括：

- 基础环境检查
- cos_setup 安装与检查
- ROS2 topic 状态检查
- 摄像头、爪子、服务状态检查
- operator_console.py 前端按钮集成
- inventory.ini 机器人清单管理
- reports/raw 原始日志保留

当前形态适合单型号、少量机器人、本地运维场景。后期如果接入更多机器人和更多型号，需要从“单机器人脚本工具”逐步演进为“机器人运维平台”。

## 2. 核心建议

推荐方向：

```text
统一入口
  -> 登录和权限
  -> 机器人总览
  -> 单台机器人运维详情页
  -> 后端任务队列
  -> worker 执行检查、安装、服务操作
```

不建议把“每台机器人一个端口”作为长期方案。多端口可以用于临时调试，但不适合作为正式运维平台的主要入口。

## 3. 为什么不建议按机器人开不同端口

如果每台机器人或每类机器人使用不同端口，短期实现简单，但长期会带来维护问题：

- 入口分散，操作员不知道该访问哪个端口。
- 登录、权限、日志、证书、监控需要重复建设。
- 每个服务实例都要单独升级和排查。
- 难以形成机器人总览页面。
- 难以做批量检查、批量安装、批量重启。
- 机器人数量增加后，端口、配置、部署容易失控。
- 很难统一记录审计日志和任务历史。

因此，多端口更适合作为开发调试或临时隔离方案，不建议作为后期主架构。

## 4. 推荐产品形态

建议使用一个统一访问入口：

```text
http://运维平台地址/
```

页面结构可以是：

```text
登录页
  -> 机器人总览
      -> G1-001 运维页
      -> G1-002 运维页
      -> 其他型号机器人运维页
```

URL 可以设计为：

```text
/robots
/robots/g1-001
/robots/g1-001/checks
/robots/g1-001/logs
/robots/g1-001/cos-setup
/robots/g1-001/services
```

前端上，操作员看到的是统一的机器人列表和每台机器人的状态。工程师可以进入单台机器人详情页查看技术日志、原始 Ansible 输出、ROS2 信息和服务日志。

## 5. 推荐技术架构

建议将系统拆成三层：

```text
前端 / operator console
  -> 展示机器人列表、任务按钮、任务状态、报告和日志

后端 control plane
  -> 管理机器人清单、权限、任务状态、日志索引和检查结果

worker 执行层
  -> 实际执行 ansible、ssh、ros2 topic 检查、摄像头检查、服务检查
```

关键点是：前端点击按钮后，后端不要在 HTTP 请求中同步执行耗时任务。

推荐任务流程：

```text
用户点击“一键检查环境”
  -> 后端创建 job
  -> job 进入任务队列
  -> worker 拉取任务并执行
  -> 执行日志持续写入文件
  -> 后端更新任务状态
  -> 前端轮询或订阅任务状态
  -> 页面展示中文日志、检查结果和处理建议
```

这样即使检查任务耗时较长，也不会卡死 Web 请求，也方便后续控制并发和重试。

## 6. 后端是否会被塞爆

单个后端不一定会被机器人数量直接压爆。真正危险的是让后端同时承担大量长时间阻塞任务。

高风险场景：

- 每次打开页面都实时连接机器人检查状态。
- 每个按钮点击都在 Web 请求线程里同步跑 Ansible。
- 多台机器人同时执行安装或完整检查，没有并发限制。
- 一个机器人网络异常，拖住整个后端请求。
- 日志大量实时写入数据库。
- 所有机器人定时任务在同一时间启动。
- 没有任务超时、取消、排队和失败隔离机制。

建议措施：

- 后端只负责轻量控制，不直接长时间阻塞执行任务。
- 耗时操作交给 worker 执行。
- 使用任务队列管理检查、安装、重启等操作。
- 同一台机器人限制并发，例如同一时间只允许一个重任务。
- 全局限制并发，例如同时最多执行 5 台或 10 台机器人。
- 任务必须有超时、取消、失败状态和可读错误信息。
- 日志优先写文件，数据库只存任务索引、摘要和最终状态。
- 页面状态使用缓存，不要每个刷新都打到机器人。
- 定时检查错峰执行，不要所有机器人整点一起跑。

## 7. 多型号机器人集成方式

不建议为每种机器人复制一整套页面和后端逻辑。推荐使用“机器人类型 + 能力声明 + 适配器”的方式。

机器人清单可以逐步从简单 inventory 扩展成类似结构：

```yaml
id: g1-001
name: 实验室 G1-001
type: unitree_g1
host: 192.168.1.10
ssh_user: unitree
capabilities:
  - base_env_check
  - cos_setup
  - ros2_topic_check
  - camera_check
  - gripper_check
  - service_check
```

另一种机器人可以是：

```yaml
id: robot-a-001
name: 其他机器人 A-001
type: other_robot
host: 192.168.1.20
ssh_user: robot
capabilities:
  - base_env_check
  - camera_check
  - service_check
```

前端根据 capabilities 显示可用按钮。后端根据 type 选择对应执行逻辑。

例如：

```text
type=unitree_g1
  -> 使用 G1 的 ansible playbook、服务名、ROS2 topic、相机规则

type=other_robot
  -> 使用该型号自己的检查脚本、服务名、topic 和安装流程
```

这样新增机器人型号时，主要是新增适配器，而不是复制整个系统。

## 8. 能力插件化思路

每个机器人类型可以声明自己支持哪些能力：

```text
base_env_check      基础环境检查
cos_setup           cos_setup 安装或检查
ros2_topic_check    ROS2 topic 检查
camera_check        摄像头检查
gripper_check       爪子检查
service_check       服务状态检查
service_restart     服务重启
log_collect         日志采集
```

前端不应该写死所有按钮，而是根据机器人能力显示按钮。

例如：

```text
G1 支持：cos_setup、ROS2 topic、摄像头、爪子、服务检查
其他机器人支持：基础检查、摄像头、服务检查
```

这样可以避免页面越来越臃肿，也能减少不同型号之间互相影响。

## 9. 数据和日志建议

建议后续将数据分成三类：

### 机器人基础信息

保存机器人 ID、名称、型号、IP、SSH 用户、末端类型、所在位置、备注等。

### 任务记录

每次操作生成一个 job：

```text
job_id
robot_id
task_type
status
created_at
started_at
finished_at
operator
summary
log_path
report_path
```

任务状态建议至少包括：

```text
queued
running
success
warning
failed
cancelled
timeout
```

### 日志和报告

原始日志继续保留在文件中，例如：

```text
logs/
reports/raw/
```

数据库或索引文件只保存摘要、路径和状态，避免大量日志直接塞进后端内存或数据库。

## 10. 登录和权限

如果只是本地单人使用，可以暂时不急着上复杂权限。

如果后期多人使用，建议至少区分：

```text
操作员
  -> 查看机器人状态
  -> 服务状态检查
  -> 服务重启

工程师
  -> 一键检查环境
  -> cos_setup
  -> 安装 / 修复
  -> 查看原始日志

管理员
  -> 管理机器人清单
  -> 管理用户和权限
  -> 配置任务并发和定时检查
```

危险操作建议继续保留二次确认，例如安装、修复、批量重启、批量升级。

## 11. 分阶段落地建议

### 第一阶段：保留当前稳定能力，补齐机器人抽象

目标：

- 保持现有 operator_console.py 和 Ansible playbook 稳定。
- 明确机器人 ID、IP、类型、能力、末端类型等字段。
- 页面上从“只面向 G1”逐步转成“机器人列表 + 当前选中机器人”。

建议结果：

```text
现有功能不变
新增机器人清单抽象
为后续多型号预留 type 和 capabilities
```

### 第二阶段：引入 job 任务模型

目标：

- 所有耗时操作都生成 job。
- 页面展示 job 状态。
- 日志按 job 保存。
- 支持任务超时、失败、完成和告警状态。

建议结果：

```text
前端按钮不再直接等待长命令结束
后端可以同时管理多个任务
任务历史可追踪
```

### 第三阶段：引入 worker 执行层

目标：

- 后端只创建任务和查询状态。
- worker 负责执行 Ansible、SSH、ROS2 检查等重任务。
- 支持全局并发限制和单机器人并发限制。

建议结果：

```text
后端不容易被长任务拖死
机器人数量增加后可以横向增加 worker
```

### 第四阶段：多型号适配器

目标：

- 为 Unitree G1 保留已有适配器。
- 新增机器人型号时，只新增对应适配器。
- 不复制整套前端和后端。

建议结果：

```text
不同机器人复用同一套平台
每种型号维护自己的检查逻辑和服务定义
```

### 第五阶段：权限、审计和批量运维

目标：

- 增加登录。
- 区分操作员、工程师、管理员。
- 保存每次操作的人、时间、机器人、结果。
- 支持批量检查和批量统计。

建议结果：

```text
工具从本地单人脚本变成可多人使用的运维平台
```

## 12. 可先不做的事情

为了避免过早复杂化，以下事情可以暂时不做：

- 一开始就上 Kubernetes。
- 一开始就拆很多微服务。
- 一开始就为每个机器人部署独立 Web 后端。
- 一开始就做复杂权限系统。
- 一开始就把所有日志塞进数据库。
- 一开始就重写现有稳定的 Ansible playbook。

更稳妥的方式是先保留当前稳定能力，再围绕“机器人清单、任务模型、worker 执行层”逐步演进。

## 13. 推荐结论

推荐最终方向：

```text
单入口 Web / Console
+ 登录权限
+ 机器人总览
+ 单台机器人详情页
+ 后端任务队列
+ worker 执行 Ansible / ROS2 / SSH 检查任务
+ 机器人类型适配器
+ 能力声明驱动页面按钮
+ 日志文件化、结果摘要化
+ 并发限制、超时和失败隔离
```

这个方案的好处：

- 不推翻当前稳定工具。
- 适合从少量 G1 机器人扩展到多台机器人。
- 适合后续接入其他型号机器人。
- 后端不会因为长任务同步执行而被拖垮。
- 操作员入口简单，工程师仍然能看到详细日志。
- 后期可以自然扩展到多 worker、多用户和批量运维。

## 14. 后续可以继续讨论的问题

后续和 GPT 或团队讨论时，可以重点围绕这些问题展开：

- 当前机器人规模大概会增长到多少台？
- 是否会多人同时使用？
- 是否需要远程访问，还是只在本地局域网使用？
- 机器人是否都能 SSH 直连？
- 是否允许在机器人端安装 agent？
- 检查任务是人工点击为主，还是定时巡检为主？
- 日志需要保留多久？
- 是否需要审计每个人的操作记录？
- 新型号机器人之间差异主要是服务名、topic、安装流程，还是系统架构完全不同？

这些问题会影响是否需要更早引入数据库、任务队列、权限系统和 worker 多实例部署。
