# No Stall Progress

## Rule

保持任务有可见进展。长任务、慢命令、排查流程、测试流程或等待外部状态时，不能长时间沉默，也不能无限等待一个没有结果的步骤。

## 强制可见进度

任何正在执行、调试、验证、等待命令、阅读大量文件、生成报告或排查问题的过程，都必须主动给用户可见进度。

- 不要等用户催问“卡了吗”“怎么不动了”才回复。
- 距离上一次对用户可见输出接近 90 秒时，就应该主动发一句短更新。
- 绝不能超过 2 分钟没有任何用户可见输出。
- 更新必须说明当前处在哪个过程，例如“正在改模板”“正在跑 py_compile”“正在等 ansible syntax-check”“正在清理验证副作用”“正在整理结论”。
- 如果只是还在等命令，必须说清楚命令还在跑、已经等到哪个阶段、下一步准备做什么。
- 如果本地验证已经完成，只剩收尾或总结，必须立即告诉用户“验证已过，正在收尾/汇总”，不要继续沉默。

## 2 分钟处理

如果已经接近 2 分钟没有对用户可见的输出或进展，必须立即选择一种动作：

- 继续往下走：选择下一个合理、低风险、可验证的步骤，并告诉用户正在做什么。
- 交给用户测试：当本地无法继续验证、需要真实设备/网络/权限/人工操作时，明确让用户测试，并给出具体命令或操作。
- 报告阻塞点：当确实无法前进时，说明卡在哪里、已尝试什么、需要用户提供什么信息。

## Long-Running Commands

运行长命令时，定期轮询输出。命令长时间无输出时：

- 说明命令还在跑、已经等待多久、为什么继续等是合理的；或者
- 停止等待并改用更直接的验证/排查步骤；或者
- 把当前可验证事项交给用户测试。

如果命令在 60 秒内没有输出但仍在运行，必须主动说明“命令仍在运行”。如果又过 60 秒还没有结果，必须再次更新，并决定继续等待、换验证方式或交给用户测试。

## User-Facing Updates

更新要短而具体，避免空话。优先包含：

- 当前状态
- 下一步动作
- 需要用户做的测试或提供的信息
- 已知风险或限制

推荐格式：

- “当前在做：<过程>。已经完成：<已完成事项>。下一步：<下一步>。”
- “命令还在跑：<命令/验证>。已等待约 <时间>，继续等到 <条件>；若无结果我会 <备用动作>。”
- “本地已经验证到 <结果>，现在在 <收尾动作>，马上给你结论。”
